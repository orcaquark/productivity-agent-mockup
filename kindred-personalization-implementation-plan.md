# Kindred personalization implementation plan

## Overview

Ship the Kindred Personalization mockups (home thread, onboarding wizard, settings screen) as a shared-backend feature across two clients: the React Native/Expo mobile app (`frontend/`) and the Tauri/React desktop app (`desktop/`). Both clients read and write the same `GET /v1/user/personalization` feed and the same settings/stated-fact endpoints. The feature includes a daily briefing, timing nudges, a weekly pattern summary, missed-task follow-ups, and kudos suggestions, backed by the existing `user_memory` contract with the productivity-agent worker. It ships behind a kill switch, following the pattern of the existing kudos suggester.

The backend and data model (§5, §6) are client-agnostic. §7 covers the mobile frontend and §8 the desktop frontend; the two can ship in either order once §6 lands.

### Architecture

Two read patterns, both already used elsewhere in the codebase:

1. **Computed on request.** The briefing, trend, and missed-task cards are assembled live in a new `personalization` handler domain, the same way `foryou.Service.GetForYou` builds cards from task and ring data. This requires no precomputation.
2. **Precomputed by cron job.** The nudge card and kudos-suggestion card are built by a cron job and read back, the same way `KudosSuggesterJob` works today. The job supplies the moment (a real task or deadline); `user_memory` supplies the policy (peak hours, nudge receptivity, tone). A dispatch ledger makes delivery idempotent across push and in-app. The kudos-suggestion targeting logic in `kudos_suggester.go` moves into a shared function so the job and the feed handler use identical decision code.

### Tech stack

- **Backend:** Go, Huma v2, Fiber v2, MongoDB driver, `robfig/cron/v3`
- **Mobile:** React Native/Expo, `expo-router`, `@tanstack/react-query`, `phosphor-react-native`, `ThemedText`
- **Desktop:** Tauri/React, React Router v7, `@tanstack/react-query` via `openapi-react-query`, `@phosphor-icons/react`, `ThemedText`, shadcn/`@base-ui/react`, Tailwind v4

No new external dependencies on either client.

### Source materials

- **Mobile:** `productivity_agent_mockup.html` (home/thread), `agent_onboarding_mockup.html` (4-step wizard), `agent_settings_mockup.html` (settings), `annotated_review.html` (design rationale, referenced as §N)
- **Desktop:** `productivity_agent_desktop_mockup.html` (home/thread + right rail), `agent_onboarding_desktop_mockup.html` (modal wizard), `agent_settings_desktop_mockup.html` (folded into the real Settings screen), `annotated_review_desktop.html` — reuses all 36 numbered notes from the mobile review unchanged, and adds one unnumbered "Desktop conversion" callout per screen

### Status

Consent, export, delete, and stated-preference endpoints already exist on the backend but have no frontend on either client. Card content — briefing text, nudge copy, trend numbers, missed-task reasons — doesn't exist yet. This is the bulk of the backend work and the one piece neither frontend can stub around.

### Deviation from the mockups

The mockups reference "closed 4 of 6 rings," but the shipped product has three rings: Plan, Do, Share (`docs/superpowers/specs/2026-05-16-productivity-score-rings-design.md`). Every task uses the real 3-ring model; mockup ring copy is rewritten accordingly (Task F3 for mobile, Task D3 for desktop).

### Conventions

| Area | Commands |
|---|---|
| Backend (from `backend/`) | `go build ./...`, `go test ./internal/handlers/personalization/... -v`, `go test ./internal/jobs/... -run TestPersonalization -v` |
| Mobile (from `frontend/`) | `bun x tsc --noEmit`, `bun test`, `bun run lint` |
| Desktop (from `desktop/`) | `bun run typecheck`, `bun test` (alias for `vitest run`) |

After any backend request/response shape change, run `make generate-api` from the repo root (regenerates `backend/api-spec.yaml` and `frontend/api/generated/types.ts`), then `cd frontend && bun run generate-types`, then `cd desktop && bun run gen:api`. Other conventions:

- Use `bun`, never `npx`, on both frontends.
- Mobile: typed `Href` for navigation, `phosphor-react-native` icons (never Ionicons), `ThemedText` semantic types (never hardcoded `fontFamily`/`fontWeight`).
- Desktop: typed `react-router-dom` routes declared in `App.tsx`, `@phosphor-icons/react` icons, `desktop/src/components/ThemedText.tsx`'s own semantic types, Tailwind utility classes over inline styles, shadcn/`@base-ui/react` primitives over hand-rolled equivalents.
- Commit after every task. The working tree is shared across concurrent agent sessions (see root `AGENTS.md`).

| Card | Compute pattern | Owner | Rationale |
|---|---|---|---|
| Today's briefing | On demand | New `personalization` domain | Same shape as `foryou`'s weekly-recap card: pull the last N days of completions/rings and template the narrative. Fetched on screen open. |

## 5. Data model changes

Everything here is backend-only and client-agnostic: one Go struct, one MongoDB collection, one set of Huma routes, read by both `frontend/` and `desktop/` through their typed clients.

### 5.1 New collection: `personalization_nudges`

Dispatch ledger for the nudge job, modeled on `kudos_prompt_dispatches` — one row per nudge sent, claimed before dispatch. Also serves as the read model for "today's nudge" in the GET handler.

Status splits into `DispatchStatus` (did the push succeed) and `UserStatus` (resolution, settable from push or in-app) because push-delivery outcome and in-app resolution can diverge independently. Undo needs the task's pre-nudge schedule captured at claim time, so a later revert can distinguish "task is still where the nudge left it" from "user already moved it again."

```go
// backend/internal/jobs/personalization_nudge_types.go
type NudgeDispatch struct {
	ID        primitive.ObjectID `bson:"_id"`
	DedupeKey string             `bson:"dedupeKey"` // unique index
	UserID    primitive.ObjectID `bson:"userId"`
	TaskID    primitive.ObjectID `bson:"taskId"`
	Trigger   string             `bson:"trigger"` // "timing_pattern" | "deadline_risk" (extensible)
	Title     string             `bson:"title"`   // "Move \"Read 20 min\" to 8:40am?"
	Body      string             `bson:"body"`
	Reason    string             `bson:"reason"` // the "why am I seeing this" text

	SuggestedAt *time.Time `bson:"suggestedAt,omitempty"` // proposed new time, if any

	// Task schedule at claim time, before any mutation. Undo compares the
	// task's current startDate/deadline against SuggestedAt — if they no
	// longer match, the task changed again after the nudge acted, and undo
	// must refuse rather than blindly restore over a schedule set on purpose.
	OriginalStartDate *time.Time `bson:"originalStartDate,omitempty"`
	OriginalDeadline  *time.Time `bson:"originalDeadline,omitempty"`

	// Job's own view: did the push attempt succeed. Independent of whether
	// the user has looked at or acted on the card yet.
	DispatchStatus string     `bson:"dispatchStatus"` // "sent" | "failed"
	PushDelivered  bool       `bson:"pushDelivered"`
	InAppSeenAt    *time.Time `bson:"inAppSeenAt,omitempty"`

	// Resolution, settable from either push action or the in-app card —
	// whichever the user reaches first. A second device reading this row
	// after resolution shows the resolved state, not a stale pending banner.
	UserStatus string `bson:"userStatus"` // "pending" | "moved" | "dismissed"

	// Count of moments that cleared policy the same day this nudge was
	// claimed, captured before the daily dispatch cap was applied — this is
	// what makes "1 of 2 today" honest. QueuePosition is this dispatch's
	// rank among that day's eligible set.
	QueueTotal    int `bson:"queueTotal"`
	QueuePosition int `bson:"queuePosition"`

	LocalDay   string     `bson:"localDay"`
	SentAt     time.Time  `bson:"sentAt"`
	ResolvedAt *time.Time `bson:"resolvedAt,omitempty"`
	ExpiresAt  time.Time  `bson:"expiresAt"`
}
```

Add these indexes to `backend/internal/storage/xmongo/indexes.go`, next to the `for_you_exposures` block:

```go
{
	Collection: "personalization_nudges",
	Model: mongo.IndexModel{
		Keys:    bson.D{{Key: "dedupeKey", Value: 1}},
		Options: options.Index().SetUnique(true).SetName("personalization_nudge_dedupe"),
	},
},
{
	Collection: "personalization_nudges",
	Model: mongo.IndexModel{
		Keys: bson.D{{Key: "userId", Value: 1}, {Key: "localDay", Value: 1}},
	},
},
{
	Collection: "personalization_nudges",
	Model: mongo.IndexModel{
		Keys:    bson.D{{Key: "expiresAt", Value: 1}},
		Options: options.Index().SetExpireAfterSeconds(0),
	},
},
```

### 5.2 Task document: reschedule counter (already exists)

No new field needed. `TaskDocument.RescheduleCount` already exists and is wired into the write path:

```go
// backend/internal/handlers/types/types.go — already present, TaskDocument
// RescheduleCount counts the times startDate or deadline was moved to a
// different value — not edits in general. omitempty, so tasks that never
```

### 5.3 `PersonalizationSettings` extensions

The existing struct covers only `Enabled`/`PausedUntil`/`ShareStruggles`. Add the settings-screen fields the mockup shows that aren't already covered by a stated fact:

```go
// backend/internal/handlers/types/types.go — extend PersonalizationSettings
type PersonalizationSettings struct {
	Enabled        bool       `bson:"enabled" json:"enabled"`
	PausedUntil    *time.Time `bson:"pausedUntil,omitempty" json:"pausedUntil,omitempty"`
	ShareStruggles bool       `bson:"shareStruggles" json:"shareStruggles"`

	// New — mockup Settings screen, "Nudges" and "Reports & briefings" sections.
	NudgesAllowed      *bool `bson:"nudgesAllowed,omitempty" json:"nudgesAllowed,omitempty"`         // default true
	QuietHoursStart    *int  `bson:"quietHoursStart,omitempty" json:"quietHoursStart,omitempty"`     // local hour, 0-23
	QuietHoursEnd      *int  `bson:"quietHoursEnd,omitempty" json:"quietHoursEnd,omitempty"`
	AutoReduceIgnored  *bool `bson:"autoReduceIgnored,omitempty" json:"autoReduceIgnored,omitempty"` // default true
	DailyBriefing      *bool `bson:"dailyBriefing,omitempty" json:"dailyBriefing,omitempty"`         // default true
	WeeklyTrendSummary *bool `bson:"weeklyTrendSummary,omitempty" json:"weeklyTrendSummary,omitempty"` // default true
	ShowScore          *bool `bson:"showScore,omitempty" json:"showScore,omitempty"`                 // default true, §29
	KudosSuggestions   *bool `bson:"kudosSuggestions,omitempty" json:"kudosSuggestions,omitempty"`   // default true
}
```

All fields are pointers, matching the existing `Enabled`/`PausedUntil` convention (nil = never answered = default on). `PersonalizationOrDefault()` needs a matching default-fill for each new field.

**`AutoReduceIgnored` algorithm:** tracked in `PersonalizationNudgeJob`'s policy step (Task B5), not as a settings field. Read the last 7 days of `personalization_nudges` for the user. If `AutoReduceIgnored` is true and at least 2 of those rows have `UserStatus: "dismissed"`, halve the effective frequency tier for the next 14 days; any `"moved"` resolution in that window resets the reduction immediately. Doesn't feed back into `nudge-receptivity` in `user_memory` in v1 (§11).

**Quiet hours** move from `KudosPolicy`'s global `DayStartHour`/`DayEndHour` constants to this per-user field. Both the nudge job and `kudos_suggester.go`'s `EvaluateKudosPrompt` read the user's value when present, falling back to the policy constants when absent (Task B1). See OQ-7 for the scope tradeoff.

### 5.4 Pause/turn-off/delete state resolver

The settings mockup has four commitment levels: "Need a break" (nudges only, via `NudgesAllowed`), "Pause personalization" (everything, timed, via `PausedUntil`), "Turn off" (everything, indefinite, via `Enabled=false`), "Delete" (permanent). Pause is broader than nudges-only and supersedes it even when `NudgesAllowed=false` disagrees on paper. Add one pure resolver next to the existing `MayShareStruggles`:

```go
// backend/internal/handlers/types/types.go
type PersonalizationState string

const (
	StateOff        PersonalizationState = "off"          // Enabled=false
	StatePaused     PersonalizationState = "paused"        // PausedUntil in the future; supersedes NudgesAllowed
	StateNudgesOnly PersonalizationState = "nudges_paused"  // Enabled, not paused, NudgesAllowed=false
	StateActive     PersonalizationState = "active"
)

// EffectiveState is the single authority every card builder and the nudge
// job must call instead of independently reading Enabled/PausedUntil/
// NudgesAllowed. Precedence: Off > Paused (everything) > NudgesOnly > Active.
func (p PersonalizationSettings) EffectiveState(now time.Time) PersonalizationState {
	if !p.Enabled {
		return StateOff
	}
	if p.PausedUntil != nil && p.PausedUntil.After(now) {
		return StatePaused
	}
	if p.NudgesAllowed != nil && !*p.NudgesAllowed {
		return StateNudgesOnly
	}
	return StateActive
}
```

`GetFeed`, `buildNudgeCard`, and the nudge job's policy check all call this instead of independently deriving the combination.

```go
// ClaimKudosDispatch atomically claims the (sender, recipient, trigger,
// subject) dedupe key so the same suggestion is never sent or resolved
// twice, whichever surface gets there first. Both KudosSuggesterJob's push
// path and the in-app resolve path (personalization.Service, Task B7) claim
// through this one function instead of each keeping its own ledger write.
func ClaimKudosDispatch(ctx context.Context, dispatches *mongo.Collection, retention time.Duration, m KudosMoment, senderID primitive.ObjectID, localDay string, now time.Time) (bool, primitive.ObjectID, error) {
	record := dispatchRecord{
		ID:          primitive.NewObjectID(),
		DedupeKey:   DedupeKey(senderID, m.RecipientID, m.Trigger, m.Subject),
		SenderID:    senderID,
		RecipientID: m.RecipientID,
		Trigger:     m.Trigger,
		Subject:     m.Subject,
		SentAt:      now,
		LocalDay:    localDay,
		ExpiresAt:   now.Add(retention),
	}
	if _, err := dispatches.InsertOne(ctx, record); err != nil {
		if mongo.IsDuplicateKeyError(err) {
			return false, primitive.NilObjectID, nil
		}
		return false, primitive.NilObjectID, err
	}
	return true, record.ID, nil
}
```

3. **`buildMissedCard`.** Query open tasks that are overdue (`deadline < now`), or have `RescheduleCount >= 2`, or have a `deadline` but no `startDate` ("no time block"), capped at 2 items.

   **Priority order for `Reason`/`Action`** (a task can trigger more than one condition): (1) overdue wins, as most time-sensitive; (2) `RescheduleCount >= 2` next — "Pushed N times — usually means it's not actually urgent"; (3) no-time-block last — "No time block set." `Action` follows the same branch: `"move_to_today"` for (1)/(2), `"add_time_block"` for (3). When ranking which 2 of possibly more qualifying tasks to show, sort by tier first, then by how overdue or how many times rescheduled within a tier.

   Mirrors the Activity-tab spec's "what slips" detector at a smaller scope (2 items, not a ranked chart), reusing its field references (`deadline`, `startDate`, `rescheduleCount`).

### Task B7: Card interaction endpoints (resolve/undo)

**Files:** modify `personalization/{types,personalization,operations,service}.go`

Four actions, matching the mockup's four resolvable cards, same request/response shape as `foryou`'s `RecordInteractionInput`/`DismissCardInput`.

(2) Compares to `NudgeDispatch.SuggestedAt` — if they still match, revert to `OriginalStartDate`/`OriginalDeadline` and reset `UserStatus` to `"pending"`. (3) If they don't match (something changed the task again since), return `409 Conflict` with a message the client surfaces as "This task changed since — undo isn't available," rather than reverting over it. 1b. **Extend the existing delete path.** `DeletePersonalizationHuma`'s service call (`settings/personalization_service.go`, currently only `s.UserMemory.DeleteMany(ctx, bson.M{"userId": userID})`) must also `DeleteMany` from `personalization_nudges` for that `userID` once that collection exists (Task B5) — otherwise "Delete all personalization data" silently leaves nudge history behind.

2. **`POST /v1/user/personalization/missed/{taskId}/resolve`** — body `{ "action": "move_to_today" | "add_time_block", ... }`; reuses the existing task-update endpoints rather than duplicating mutation logic. A thin, personalization-flavored wrapper that logs which suggestion the user acted on (a useful signal for the worker later; write-back is out of scope, §11).
3. **`POST /v1/user/personalization/kudos/resolve`** — body `{ "friendId": "...", "action": "sent" | "skipped" }`. Both actions must claim the dispatch ledger first, via the same `jobs.ClaimKudosDispatch` the cron job uses (Task B4 step 2b), so the cron job can't independently re-detect and re-push the same moment shortly after:
   - Re-derive the `KudosMoment` for `friendId` the same way `buildKudosCard` did (via `jobs.BestKudosSuggestion`), so the claimed dedupe key matches what the job would use.
   - Call `jobs.ClaimKudosDispatch(...)`. If it fails (already claimed — likely the cron job's push beat the user to it), that's not an error: honor the user's tap regardless.
   - On `"sent"`, call the existing encouragement-send path exactly as if sent from the Kudos screen, regardless of whether the claim above was this call's own or pre-existing.
   - On `"skipped"`, the claim alone is the entire effect — it occupies the dedupe key so the cron job won't re-surface this moment inside its normal cooldown window.

```ts
// frontend/hooks/usePersonalizationFeed.ts
import { useQuery, useQueryClient } from "@tanstack/react-query";
import { request } from "@/hooks/useRequest";
import type { PersonalizationFeed } from "@/api/personalization";

export function usePersonalizationFeed() {
    const queryClient = useQueryClient();

    const { data, isPending, error, refetch } = useQuery({
        queryKey: ["personalization"],
        queryFn: async () => (await request("GET", "/user/personalization")) as PersonalizationFeed,
    });

    async function resolveNudge(dispatchId: string, action: "moved" | "dismissed") {
        await request("POST", `/user/personalization/nudge/${dispatchId}/resolve`, { action });
        queryClient.invalidateQueries({ queryKey: ["personalization"] });
    }

    // Uses a dedicated undo endpoint (Task B7) rather than reusing resolve,
    // since only a dedicated endpoint can distinguish "undo is safe" from
    // "the task changed since the nudge was accepted" — returning 409 in
    // the latter case rather than silently reverting.
    async function undoNudge(dispatchId: string): Promise<{ ok: true } | { ok: false; reason: "changed_since" }> {
        try {
            await request("POST", `/user/personalization/nudge/${dispatchId}/undo`);
            queryClient.invalidateQueries({ queryKey: ["personalization"] });
            return { ok: true };
        } catch (e) {
            if (isRequestError(e) && e.status === 409) {
                return { ok: false, reason: "changed_since" };
            }
            throw e;
        }
    }

    async function resolveMissed(taskId: string, action: "move_to_today" | "add_time_block") {
        await request("POST", `/user/personalization/missed/${taskId}/resolve`, { action });
        queryClient.invalidateQueries({ queryKey: ["personalization"] });
    }

    async function resolveKudos(friendId: string, action: "sent" | "skipped") {
        await request("POST", "/user/personalization/kudos/resolve", { friendId, action });
        queryClient.invalidateQueries({ queryKey: ["personalization"] });
    }

    return { feed: data, loading: isPending, error, refresh: refetch, resolveNudge, undoNudge, resolveMissed, resolveKudos };
}
```
